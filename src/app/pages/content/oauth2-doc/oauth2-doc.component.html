OAuth 2.0 — What & Why

OAuth 2.0 lets an application (the client) obtain limited access to a protected API on behalf of a user, without learning the user’s password. It uses short-lived tokens to represent permission.

Key Roles

  • Resource Owner: The user who owns the data.
  • Client: Your app or website that wants to access data.
  • Authorization Server: Issues tokens (e.g., Keycloak).
  • Resource Server: The API that validates tokens and serves data.

Common Grants (Flows)

  1. Authorization Code (web apps, supports PKCE): user signs in → app gets a code → exchanges for tokens.
  2. Client Credentials (machine-to-machine): app itself obtains a token to call backend services.
  3. Refresh Token (token, not a flow): used to obtain new access tokens without another login.

Tokens

  • Access Token: Presented to APIs; usually short-lived.
  • Refresh Token: Lets the client get new access tokens; never send it to APIs.
  • ID Token: (added by OIDC) describes the authenticated user for the client.

Tip: Always use HTTPS, store tokens safely, and request only the scopes you need.

Best Practices

  • Prefer Authorization Code + PKCE for browser login.
  • Keep access tokens short-lived; rotate refresh tokens.
  • Follow least privilege with scopes.
