OpenID Connect (OIDC) — What & Why

OpenID Connect is an identity layer on top of OAuth 2.0. It lets a client application verify a user’s identity and obtain profile information in a standard, interoperable way. OIDC adds the ID Token, a signed token that tells the client who the user is, plus a UserInfo endpoint for additional claims.

Key Roles

  • End-User: The person who is authenticating.
  • Relying Party (RP): Your app (SPA) that needs to know who the user is.
  • OpenID Provider (OP): The identity server that authenticates users and issues tokens (e.g., Keycloak).
  • Protected API: Optional backend that accepts the OAuth access token for data access.

How OIDC Works (SPA-friendly)

  1. Authorization Code + PKCE: The RP sends the user to the OP’s authorize page with scope=openid (and often profile email).
  2. Callback: After login/consent, the OP redirects back with a code.
  3. Token Exchange: The client exchanges the code for tokens: ID Token (who the user is), Access Token (call APIs), and optionally a Refresh Token.
  4. Claims: The client reads user claims from the ID Token and/or the UserInfo endpoint.

Tokens & Endpoints

  • ID Token: JWT that asserts the user’s identity (subject, issuer, nonce, etc.). For the client.
  • Access Token: Presented to APIs for authorization. Short-lived.
  • Refresh Token: (if issued) Used to obtain new tokens without re-login.
  • Discovery: /.well-known/openid-configuration publishes all OP endpoints and capabilities.
  • UserInfo: Standard endpoint to fetch additional user claims with the access token.

Scopes & Claims

  • Scopes: openid (required), plus profile, email, etc. control which claims you get.
  • Claims: Attributes about the user (e.g., sub, name, preferred_username, email), delivered in the ID Token or via UserInfo.
